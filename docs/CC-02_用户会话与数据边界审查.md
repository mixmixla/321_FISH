## 给 Pro 的结论与决定入口

当前已经解决管理员凭据、Web token 绑定原 Session、本端显式退出、最后 UID 端的运行资源清理，
以及一对一文件鉴权和公共游戏生命周期。剩余 CC-02 核心是**身份退役后怎样阻止旧数据重新归属，以及哪些数据应保留**。
现有“删除账号不可恢复”文案超出实现：删除 `known` 不会删除 `nick_to_uid`，同昵称可以重新登录并取得旧 UID；
草稿、定时消息、云历史及本地昵称目录仍可留存。不能把已完成的注销修复视为删号/持久数据模型已完成。

建议最小候选是分开处理“踢全部现有端”和“退役身份”：沿用 UID/Session/协议，加入最小持久退役标记及登录/写入屏障，
先阻止旧 UID 自动复活和后台消息继续发送；共享数据和物理文件按单独保留表处理。本次没有批准这一选择。
同昵称重注册、实际数据擦除和客户端迁移需要明确决定，不能靠删除目录或把 `known.pop` 改成删除映射来解决。
决定表 D1–D11 在下文；Pro 可逐项选定或给出替代方案，再冻结实现包。

## 术语与权威关系

| 术语 | 本材料的精确定义 | 归属与限制 |
| --- | --- | --- |
| 用户身份 | 单台 Hub 中由昵称映射关联的逻辑身份；当前没有独立全球账号 ID | 登录凭据、角色、UID 相关数据由服务器裁决 |
| 昵称 nick | 当前登录/自动注册的查找键，同时用于展示及客户端本地 profile/路径 | 不是跨服务器唯一身份，也不能代替不可变数据主键 |
| UID | Hub 分配的整数，普通昵称重登复用 `nick_to_uid`；分配序号可落快照 | 同 UID 可以有多个端；不同服务器或丢失状态后相同整数不代表同人 |
| known | 服务器已知用户资料目录，含昵称、状态、普通密码摘要等 | `known` 存在与否不是完整的账号存活约束 |
| Session | 一个已认证 TCP 或 Web 端的运行对象 | `sessions[uid]` 只是代表，`_uid_clients[uid]` 才是端集合 |
| Web token | 绑定具体已认证 Web Session 的 bearer 凭据 | 不代表永久账号；不保存到服务器快照；不能借其它同 UID 端续权 |
| 本端退出 | 注销该 Session 并撤销其 token | 其它端在线与持久数据保留 |
| 最后端离线 | 同 UID 无活端后清运行资源并通知 | 不等于删号，不清草稿/历史/云数据 |
| 踢人 | 当前实现注销代表端；产品目标可能是踢全部现有端 | 不等于封禁，是否阻止重新登录需另决定 |
| 退役 / 删除 | 候选：旧身份停止认证和写入；删除数据另按表规定 | 不混同注销、清消息、封禁和物理擦除 |

## 身份与会话事实

| 路径 | 当前事实 | 源码依据 |
| --- | --- | --- |
| 分配/重登 | `_attach`允许同昵称多端；已有`nick_to_uid`就复用UID，否则递增序号。没有独立账号改名接口，换登录昵称按另一个查找键处理 | [server.py](../server.py)：1525 `_attach`；638 `_restore` |

| token活性 | token指向原Web Session，验证它仍活跃；logout/unregister逐Session撤销。token和Session集合不落快照，重启后不恢复 | server.py：1945 `session_by_token`；[web.py](../web.py)：5945 `_logout` |
| SSE与idle | 页面刷新/断开只detach；SSE ping/touch保活，idle清扫另用`min_idle`复查。关闭页面不等同明确退出 | web.py：7519 `_events/_sse_loop`；server.py：6791 `_sweeper_loop` |

| 资料保留 | 最后端注销重建`known[uid]`为nick/last_online，只复制pwd；sign/avatar/invisible/status/remarks等原资料没有统一保留 | server.py：1981–1987；这是本次静态观察，未动态复现 |
| 管理员踢人 | 只取`sessions[uid]`代表端发送kicked、注销并close；其它端/token可存活，没有禁止将来重登状态 | server.py：3417 `_on_admin_kick` |
| 管理员删号 | 退群/转群主或空群解散，清作者UID消息；抓取全部端、撤销目标UID全部Web token后逐端注销，最后`known.pop`并force持久化 | server.py：3648 `_admin_del_remove_groups`、3666 `_on_admin_user_del`；374 `ChatBus.clear_uid` |
| 删除后的重登 | 昵称映射保留，known密码条目已删；同昵称可免密登录并复用旧UID、重建known。删除/登录各阶段分开锁区，没有持久退役屏障 | server.py：1525、1613、3666；复活是静态调用链结论，竞态结果待受控验证 |
| 管理入口/UI | 删除账号入口在桌面，确认文案称“不可恢复”；Web管理REST提供kick/clear_uid/clear_all，没有user_del路由。Web收到kicked/deleted仅显示error，默认close_conn为空，不主动清SSE/登录视图 | [client.py](../client.py)：10107–10205；[client_core.py](../client_core.py)：2511–2532；web.py：6871–6955及PAGE error处理 |
| 密码并发 | 首次认领先查无密码再独立写入；多端改密先校验旧密码再写入，没有原子比较更新；改密不主动撤销已有端/token | server.py：1608–1655、1685 `_on_set_pwd`；并发胜者/失败策略待决定 |

删号“抓取当前全部端/token”已修，不代表并发新登录/已经通过活性检查的请求都被原子阻止。
`dispatch`入口活性检查也不能单独代替提交时身份验证。Web端撤权后的REST会失败，但现有SSE/UI不一定立即回登录；
后续Task若承诺即时退出，需要客户端/Web失效行为证据，不能只核对服务器token表。

## 风险与最小场景

| 场景 | 静态结论 / 风险推断 | 后续验证要求 |
| --- | --- | --- |
| 同昵称删号后重登 | 旧UID复用且密码条目缺失；仍按旧UID取草稿/云数据。云正文是否可解密另取决于备份口令 | 合成账号先建数据再删号，旧token失败；按D1重登拒绝或新UID，不继承私有数据 |
| 删号同时登录/写入 | 删除分阶段锁区；抓取端集合后可能有新attach，检查后写入或迟到cloud IO也可能复建数据 | 用屏障覆盖每个提交窗口，不用固定sleep；旧端不得发消息/建资源/落文件 |
| 被踢者有TCP+2Web | 当前只移除代表端；Web error未主动收口视图 | 全端撤销及每个UI回登录；他人和管理员保持，后续登录按D2 |
| 删除后定时消息到期 | `_sched_still_valid`检查拉黑/群成员，未检查作者身份仍存活；public/private可继续发送 | 退役取消队列，并阻止已经取出的due项在退役提交后发布 |
| 正常最后端离线再登录 | `known`资料重建丢除pwd外字段；本体头像文件仍可能存在 | 独立验证签名/头像/状态/remarks等逐项，按D9明确保留策略 |
| 两端同时首登/改密 | 检查和写入不在同一原子边界；首登均成功/末写覆盖有可能 | 按D8给出认证提交规则；失败端不能借先attach取得写权限 |
| 重启或降级 | Session/token不恢复；昵称/UID/private状态可恢复；旧版本不认识新增退役记录 | 旧快照向前兼容、新快照重启仍拒旧身份、降级不重新放行 |
| 昵称碰撞/换名/跨服务器 | 本地安全昵称目录/Profile与服务器UID不是同一个键；相同UID整数/消息seq可属于不同Hub | D5决定独立命名空间、未归属旧目录的迁移策略，不自动合并 |
| state.json真实重启 | groups.members/mutes与reads内UID键恢复为字符串，运行逻辑常按整数检查；现有测试还断言字符串键 | 在真实JSON往返后继续群发送/管理/禁言/已读操作，关闭类型与权限风险；D10 |
| 云包或断点归属不同 | cloud_restore未比对身份；下载meta无账号/服务器绑定 | 错UID/错scope/旧代际/旧blob兼容矩阵；不把正常恢复测试当归属验证 |
| 物理IO失败 | `ServerStore.save`对写入/replace的OSError静默返回；Hub force调用无成功回执。注释“返回即持久”不能证明IO成功 | 合成store写/替换失败、重启、旧快照与晚到写屏障；失败不得报告已持久删除 |

最后一项依据 [server_store.py](../server_store.py)：27–53与server.py：932–1021。
旧worker已取出的快照与force写入的提交顺序也须受控核验；本次没有将潜在旧快照覆盖问题宣称为已动态复现漏洞。

## 最小方案候选与取舍

| 候选 | 行为与成本 | 评价 |
| --- | --- | --- |
| M0 仅澄清文案、保持当前删号 | 不加持久身份约束；旧昵称/UID与关联数据继续可恢复 | 可作临时说明，不能满足“旧身份不可复活/私有数据不继承”的完成条件 |
| M1 保留旧UID，持久退役并保留昵称（建议送审） | 昵称映射仍指旧UID，但退役标记优先于密码/自动注册；撤销全部端并阻止后续写入/后台发送。按决定表清私有数据或保留在不可访问状态 | 不需重新编号或全量迁移，旧客户端可消费既有error；新增快照兼容和并发屏障，需Pro批准 |
| M2 真删除，昵称再注册分配新UID | 移除旧昵称认领能力；UID序号不回退。旧数据保留旧UID/墓碑，不迁给新UID | 服务器可隔离两代身份，但客户端按同昵称目录/Profile仍会混用；必须联动本地身份和迁移，不宜自动归入最小首批 |

M1 的候选步骤（未执行）：

1. 单独修正踢人操作为抓取并撤销目标 UID 的全部现有端/token，保持可重新登录的“强制下线”语义；
   如果要禁止重登，另用退役/封禁状态，不暗中增加踢人冷却期。
2. 在现有 Hub 中建立最小退役记录，所有登录路径先校验；普通已有活跃账号/稳定 UID 不迁移，管理员及 bot 保留身份另设保护。
   旧快照缺少记录解释为没有新增退役记录，不能由 `known` 缺失自动推断全部旧 UID 已删除。
3. 退役标记、当前端授权撤销、禁止新端加入与 UID 私有数据修改构成一个明确提交边界；
   不持 Hub 锁执行网络/磁盘 IO。已通过dispatch活性检查但尚未写入的请求、到期队列和云IO都要验证提交时身份。
4. 按D3决定处理草稿、定时任务、云密文及私有偏好；按D4保留/清共享内容和引用。
   先冻结清单，再实现；旧UID不得在重新注册时自动“继承”数据。
5. 快照可读旧格式，新增退役字段与写失败反馈必须验证；新状态回滚旧服务会绕过退役记录，
   因而不能把“旧版本仍能解析JSON”称为安全降级兼容。回滚需要版本门槛或停服受控恢复方案。

物理文件删除涉及快照与独立文件两个持久介质，不能声称单一原子事务。
最小首批可先保留云blob等物理文件但切断访问并明确“逻辑退役，未物理擦除”；
若选择物理擦除，必须规定IO失败时的结果、可重试清单和不让旧快照/晚到上传复活文件的顺序。
这项取舍由D3/D7决定，不由主控替用户决定保留或删除。
