## 3. D1–D11 技术方案决定

### D1 — 身份退役

选择 M1，不采用仅改文案的 M0，也不在首批采用开放同昵称重注册的 M2。

- 应用层不可恢复退役，保留旧登录名和旧 UID 的退役关系；无自助恢复入口。
- 退役判断优先于普通免密登录、密码检查与首次认领，并在真正 attach/授权提交处复查。
- UID 分配不得复用已退役身份；恢复序号与身份映射必须保持一致。
- 旧快照缺少新增退役字段时，不能仅凭 known 缺失推断该身份已被删除。
- 明确保护现有管理员保留身份及实际系统/bot 身份，具体集合由实现前源码核对确定。
- UI 不再承诺“删除全部数据、不可恢复”。改为准确的“退役账号/禁止再次登录”，并说明清理和保留范围。

这是后续 RETIRE 的方案选择，不是对真实账号执行退役的授权。

### D2 — 踢人

选择“强制下线目标 UID 在撤权提交时存在的全部会话，允许以后重新认证”。不是封禁，不暗中增加冷却期。

- 在一个明确锁内提交点确定目标集合并使这些 Session/token 失效；网络通知及连接关闭在锁外处理。
- 提交点之后新完成的、通过正常认证的登录允许存在，不得被迟到的旧会话清理误伤。
- 旧会话不得在撤权后提交新请求；提交点之前已经被业务接受的操作，不笼统承诺追溯取消。各异步操作边界需要写清，不能把 KICK 扩大为完整 RETIRE。
- 当前受支持客户端收到强制下线信号后停止自动恢复该旧登录，进入可手动重新登录的状态。
- 可达客户端验证事件驱动退出；断网客户端在收到失效事件或下一次认证失败后收口。不能承诺离线界面瞬时变化。
- 保留单端 logout 仅影响本端，以及 SESSION-02 的最后端清理/重登保护。

### D3 — UID 私有数据

首批 RETIRE 选择“必要记录逻辑清理 + 遗留物理文件隔离”，不做广泛物理擦除。

| 数据 | RETIRE 目标 |
| --- | --- |
| Session / Web token | 撤销全部现有端；退役身份不得产生新认证端/token |
| 服务器定时消息 | 取消该 UID 排队任务；已经取出的 due 项在发布提交前也必须检查退役/待提交状态 |
| 服务器草稿 | 清除该 UID 所有的草稿记录，并拒绝后续读写；反映在成功持久提交后的当前快照中 |
| 普通密码摘要、该身份拥有的私有偏好 | 从活跃账号记录移除；只保留必要退役信息。按实际字段冻结清单，不清除他人持有的引用 |
| 云密文文件 | 首批可以保留物理文件，但所有访问、上传提交和启动索引恢复都不得使退役 UID 重新取得访问权 |
| 备份、审计、下载副本 | 不承诺随本次操作擦除；与当前快照的逻辑清理区别说明 |

云历史即使加密也属于需要管理的数据；保留密文不能表述成“数据已经删除”。文件物理 GC 若有必要，另经归属与失败恢复方案审查。

### D4 — 共享数据

维持当前清除目标作者消息的既有兼容行为，不扩大为删除整段私聊或他人消息。群主转让、空群解散按现有已验收规则执行。

群任务、投票、共享附件、动态、贴纸等未获本次明确清除决定的内容保留，保留旧作者 UID 引用；必要时显示已退役作者。不得把共享资源的存在反向用作该身份仍有效的依据。

无可靠上传者/引用索引的文件，不凭文件名、fid 或目录猜测归属后批量删除。审计维持原保留策略，不为了证明删除而改写历史。服务器不能承诺远程擦除客户端副本。

### D5 — 本地数据隔离

本批不迁移本地目录，不引入 server_id 协议字段。后续 LOCAL 设计应评估稳定服务器范围 + 服务器内身份，而不是昵称目录或单独的整数 UID。

host:port 只能作为连接地址/可能的临时边界，不能冒充稳定服务器身份。旧无归属目录、Prefs、E2EE 密钥和下载断点不得自动认领、合并或删除。

M1 不会解决当前同昵称跨服务器混用问题；后续版本不能因此宣传完整跨账号/跨服务器本地隔离。

### D6 — 改密与 token 撤销

首批不改变普通改密对已有端的产品语义，不实现持久 token、轮换或新的过期体系，不移除既有兼容认证入口。

保留 CC-01A 部署管理员凭据规则和 SESSION-01 的显式单端退出。后续若决定“改密退出所有设备”，须将全端撤权、UI 重认证和并发策略作为单独明确范围，而不是顺手加入。

### D7 — 持久化失败、回滚与切分

持久提交可靠性是 RETIRE 的直接前置/组成部分，不是低优先级优化，也不是全面存储重写。

- 建议用运行态待提交屏障先阻止新认证与迟到写入，再在锁外完成有顺序保障的持久化。
- 只有可确认的持久退役提交成功，才能报告退役成功；仅内存撤权不等于持久完成。
- 写入/replace 失败必须传播到管理结果。不得静默成功，不得自动重新放行当前已阻断身份；应明确处于失败/待重试状态。
- 首次持久提交从未成功时，不得承诺崩溃或重启后退役状态仍存在。恢复策略、重试与运维限制必须如实说明。
- 旧 worker 快照不能覆盖更新的退役记录；后台写和强制写需要共享可验证的提交顺序保障。
- 不持 Hub 全局锁进行网络或磁盘 IO。
- 新版读取旧快照兼容，不等于旧版运行新快照安全。仅加 schema 字段无法约束完全不识别该字段的旧二进制。
- 完成退役后的实例禁止无审查直接降级旧服务；回滚限保留新身份约束的修复版，或停服受控恢复。不得把旧备份直接覆盖成普通回滚步骤。
- 未启用/无法使用必要持久化时，不提供“永久退役成功”的反馈。

### D8 — 首次认领与改密并发

单列 CC02-CREDENTIAL 高优先级任务，本批不顺手改造。后续采用明确的原子提交方案：首次有效认领以成功提交者为准，竞争者按最新凭据重新验证；改密以当前凭据版本/记录的比较提交避免静默覆盖。

不能先把失败方 attach 成已授权 Session，再事后宣布其认领失败。密码派生工作不应因耗时计算长期占用 Hub 全局锁。

保留免密使用模式时，必须承认它不提供“只有本人能认领这个昵称”的身份保证；稳定 UID 不等于认证强度。RETIRE 对退役身份的提交屏障不能等待这项一般凭据并发改造才实现。

### D9 — 正常注销的资料保留

纳入首批 PROFILE。以原 known 记录为基础更新 last_online 等明确运行字段，保留 nick、pwd、sign、avatar、invisible、status、remarks 等已有应持久信息，实际字段以源码清单为准。

公开显示的在线/离线状态仍以活跃会话判断，不能因保留 busy 等偏好而将已离线用户显示为在线。不要把 Session/token 等运行对象写入持久资料。

不改变最后端退群、群主转让等当前产品语义。永久群成员关系属于另一个产品决定。

### D10 — JSON 恢复后的键类型

纳入首批 RESTORE。先核对完整字段白名单，再规范化实际应为 UID/GID 的映射键；不对所有字符串键递归 int()。

至少覆盖材料指出的 members、mutes、reads，并检查其外层结构；昵称键、频道键、资源 ID 等按自身类型保留。非法或归一化冲突记录须明确处理，不得宽松授权或静默掩盖。

先建立真实 JSON 写盘/恢复后继续执行群发送、成员/管理权限、禁言、已读的回归用例；验收重启前后行为，而不是仅把测试中的字符串期望改成整数。

### D11 — 云恢复归属

与 LOCAL 联合另审，不在 RETIRE 中新增云包格式。未来明确区分同身份 restore 与跨身份显式 import；不能用单独 UID 比较替代服务器范围和身份代际判断。

旧 blob 缺少范围信息时不能自动证明属于当前身份。其兼容读取、人工确认、导入映射与备份策略须另行冻结，不能无声拒绝所有旧数据，也不能透明 merge。

本次 RETIRE 必须阻断退役身份的 CLOUD 访问/迟到提交，但不据此声称已解决跨账号或跨服务器云导入安全。

## 4. 建议首批：CC-02A 基础一致性

仅包含三个切片，建议 PROFILE → RESTORE → KICK，顺序实现并分别审查。

| 切片 | 主要范围 | 必须保持/验证 |
| --- | --- | --- |
| PROFILE | server.py 注销资料更新、相应测试 | 单端/最后端、重连/重启的资料保持；不改变退群与多端资源语义 |
| RESTORE | server.py 恢复映射、真实 JSON 行为测试 | 重启后合法/非法操作及禁言/已读一致；不放宽权限 |
| KICK | server.py 撤权、必要 web.py/client_core.py/client.py 失效交互、专项测试 | TCP+两个Web全端失效；他人存活；提交后重登可用；UI不自动恢复被撤销登录 |

每个观察先在合成数据上核验；已修问题不重复实现，不能复现的风险不得伪称确定缺陷。涉及同一 server.py 的切片使用唯一写入者，不让多个编码代理同时覆盖。

本批排除：身份退役实现、物理清理、UID重新分配、普通密码策略变化、本地迁移、云格式、游戏入口筛查、EXE和新功能。

冻结 Task 须补齐：准确基线、允许文件/必要辅助模块、行为不变量、测试矩阵、UI边界、最终门禁与原始证据、审查角色、外部动作权限。不是把本文件直接标 READY。

## 5. 下一主线：CC02-RETIRE

首批之后优先进行，不放入无限期 Backlog。包含必要的持久提交可靠性子步骤（可在 Task 内称 STORE-COMMIT），先审查顺序/失败设计，再实现 M1。

必须提供写入面清单：登录与 attach、普通 dispatch 写入、直接 Web API、已取出的定时消息、CLOUD 文件提交及快照 worker。逐项标明最终授权检查与提交边界，不能只在 dispatch 开头添加一条 if 就宣称全部交错安全。

采用 Event/Barrier 等可控交错验证，不用固定 sleep 证明竞态不存在。成功后必须在真实 JSON/独立临时目录重启检验退役状态；失败不能误报持久成功。

RETIRE 完成前，不宣称当前“删除账号”已经安全关闭，也不发布新增不可恢复删除承诺。
