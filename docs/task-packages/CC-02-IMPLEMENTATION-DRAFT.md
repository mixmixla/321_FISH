| D6 | 保持普通改密对已有端语义；不加持久token/轮换/过期体系，不移除兼容入口，部署管理员规则不变 |

## 首批与后续切分

- 已批准CC-02A：PROFILE→RESTORE→KICK，准确基线/文件归属/行为与验证见冻结Task。
- 紧接下一主线CC02-RETIRE：M1和STORE-COMMIT，先冻结可靠提交设计/全写入面/失败重试/回滚，再批准实施。
- 高优先级CC02-CREDENTIAL：独立原子认证提交设计与授权，不能顺手混入首批。
- CC02-LOCAL/CLOUD：另行设计服务器范围/身份代际/restore-import、无归属旧数据的兼容与迁移；真实操作权限另授。
- VB-01仍单独候选，不因本决定启动；游戏入口/EXE/发布均不在本批。

## RETIRE 草案：必须冻结的成功/失败与数据表

1. 运行态pending屏障先阻止新认证及退役UID迟到写，不在Hub全局锁做IO。
2. 登录/attach、dispatch与直接Web写入口、已取due、CLOUD文件提交及快照worker分别列最终授权与提交点；入口一条if不能证明全部安全。
3. 删除草稿/取消sched、清活跃密码/私有偏好，保留最小退役信息；普通共享引用/作者消息清理按D4，不触真机数据。
4. 云blob首阶段物理保留，逻辑访问/启动恢复/上传提交拒退役；备份、审计、下载副本仍可存在，UI不承诺物理擦除。
5. STORE-COMMIT的正常/force/后台写共享可验证顺序；写/replace失败不能静默成功，不能把内存撤权当持久成功，阻断身份保持失败/待重试。
6. 必要持久化未启用或不能确认成功时，不报告永久退役成功；首提交从未成功的重启风险必须明示。
7. 用Event/Barrier和真实JSON/独立目录重启检验；旧字段向前可读，新退役快照不能安全降级旧程序。
   回滚仅保留身份约束的修复版或停服受控恢复，不把旧备份覆盖当普通回滚。

当前“删除账号”的旧UID复活/私有数据/后台提交风险仍未解决；M1技术决定和首批通过均不能宣布RETIRE安全关闭。
本草案及决定不额外授权commit/push/PR/merge/release、真实迁移/删除、外部消息或heartbeat。
