# 321_FISH 路线来源与任务映射

更新日期：2026-10-01（Asia/Shanghai）

## 文档定位

这是一份供跨聊天恢复上下文使用的脱敏路线索引。它记录 Pro 方向、用户已经确认的节点、
当前交付与候选任务之间的对应关系，帮助新会话理解“为什么有这些任务”。

它不是执行状态源，也不产生 READY、ACCEPTED、MERGED 或发布结论。实际状态、执行者、
下一动作和权限只看 [AI 指挥中心](AI_COMMAND_CENTER.md)；冻结目标看
[Task Packages](task-packages/)，命令与结果看 [Review Packages](review-packages/)，稳定架构事实看
[PROJECT_MEMORY](../PROJECT_MEMORY.md)。本文件不复制私有聊天全文、会话标识、凭据、用户数据或运行日志。

## 任务映射与边界

### CC-01：公开安全与验证基线

当前已落地的正式子任务是管理员凭据和公开仓库安全整改：部署侧凭据、缺失配置 fail closed、
TCP/Web 认证一致性、Session/token 边界、相关测试与公开仓库文档。CC-01A-FIX-01 只补齐验收
证据和 R26 测试等待竞态，不扩大管理员任务。

对应资料：

- [CC-01A Task](task-packages/CC-01A.md)
- [CC-01A-FIX-01 Task](task-packages/CC-01A-FIX-01.md)
- [CC-01A r2 Review](review-packages/CC-01A-r2.md)
- [当前验收状态](AI_COMMAND_CENTER.md)

CC-01A 的通过只表示该任务达到其验收范围，不表示 R0 的所有验证、真实部署或后续产品阶段已经完成。

### R1 现有交付与 CC-02 Architecture Review

BATCH-R1 是用户明确允许连续推进的生命周期批次，Task 本身覆盖：

- 当前 Web Session 的显式退出和逐 Session token 撤销；
- 最后存活端的 UID 资源清理、下线通知和重连竞态；
- 现有游戏公共终局、复位、退出确认和重入；

同一 R1 交付中另有：

- FILE-AUTH-01 独立完成，属于同 R1 交付；它不扩大 BATCH-R1 Task 的上述三项范围。

对应资料：[BATCH-R1 Task](task-packages/BATCH-R1.md)、[BATCH-R1 Review](review-packages/BATCH-R1-r1.md)。

这些实现提供了当前身份/Session 行为事实，但没有完成下一项 CC-02 的设计审查。CC-02 的最小审查
输出应包括：

1. 当前账号、UID、Session、token、TCP/Web 多端关系的事实清单；
2. 聊天历史、草稿、定时任务、云端数据等持久数据的归属、生命周期和迁移边界；
3. 账号删除、重新登录、跨端退出及旧数据清理的最小方案；
4. 明确禁止顺手改动的协议、账号模型、真实数据和客户端范围；
5. 一份可供后续实现的 CC-02 Task Package、验收矩阵和独立审查边界。

CC-02 是“先设计再实现”的架构审查项。它需要新的冻结包和 READY 状态；本文件不会把它放行。

### CC-03：公共游戏流程与 47 个入口筛查

CC-03 处理现有公共游戏流程是否一致、各入口能否到达、权限/断线/终局行为是否有证据覆盖，
并对 47 个游戏入口做分类筛查。BATCH-R1 只验证了其批准的公共生命周期路径，不能代替 CC-03
对全部入口的结论。CC-03 尚未形成当前 READY 的实现范围。

### CC-04：旗舰游戏与低打扰 UX

CC-04 对应五子棋、四子棋，以及 Excel 工作表、收起和低打扰体验设计。它需要先明确游戏规则、
入口分类、交互边界、协议影响和验收方式；不能把已有 UI 草案或少量真实页面验证直接当成 CC-04
实施授权。当前仍属于方向/设计候选。

### CC-05：测试与 EXE 验证

CC-05 负责验证基线、门禁报告可靠性、打包产物和 Windows 试用前置条件。当前 VB-01 可视为其
验证基线候选，也可以在依赖和权限满足时单独提出并行 Task；“可并行候选”不等于已 READY。
EXE、真实局域网、设备和长期负载必须有独立环境证据，不能用普通 pytest 通过替代。

## 当前优先级和放行规则

按现有方向恢复工作时，顺序是：

1. 保留 R0/CC-01 的验收和历史证据；不重复已完成的安全整改。
2. 按 Pro 路线先准备 CC-02 Architecture Review，明确持久数据与迁移边界；实施仍需新 Task Package 和 READY。
3. 在 CC-02 结果和新 Task Package 基础上拆解 CC-03 公共游戏/47 入口筛查。
4. 之后进入 CC-04 旗舰游戏与低打扰 UX 设计和实施准备。
5. CC-05/VB-01 可在依赖清楚时提出并行验证包；真实 Windows 试用仍需 R3 的部署权限。
6. R4 在试用反馈形成后再拆分，不提前创建产品功能。

每一项都必须经过当前指挥中心的 PROPOSED → READY → IMPLEMENTING → REVIEWING → ACCEPTED
流转。没有对应的 READY Task Package 时，只做调查或记录，不修改实现范围。候选表中的
GAME-UI-01、VB-01、REL-01 以及本文件列出的 CC-03–CC-05 均不因被映射而自动获准开工。

## 历史建议的纠偏

早期“仓库功能审查”聊天中曾建议在 CC-01A 后顺序推进 `CC-01B（公开文档/安全整理）`、
`CC-02（测试可靠性）`，并讨论让 Codex 在小任务上自动继续。这些内容是当时助手给出的流程/示例，
不是当前用户确认的产品路线。当前索引采用原 Pro 路线中的 CC-02 定义，即用户/Session/持久数据边界
的 Architecture Review；这不表示该架构批次已经获准实施。测试与 EXE 验证归入 CC-05/VB-01 候选。
历史建议不覆盖现行指挥中心和新 Task Package。

## 跨聊天恢复最小清单

新会话恢复时按以下顺序核对：

1. 读取 `AGENTS.md`、`COLLABORATION.md` 和 [AI 指挥中心](AI_COMMAND_CENTER.md)。
2. 读取当前任务对应的 Task Package 和最近 Review Package，核对 base/head、文件所有权、dirty 状态和活动进程。
3. 用本文件判断任务来自哪一阶段、属于建议还是已确认方向；不要用本文件判断 READY 或验收状态。
4. 仅在指挥中心明确放行后编辑；遇到账号、协议、迁移、产品规则或真实部署权限问题，先形成决策材料。
5. 交付时回写 Task/Review/指挥中心的对应位置；本文件只在路线来源或映射发生变化时由主控更新。
